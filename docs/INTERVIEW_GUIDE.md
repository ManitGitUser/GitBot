# GitBot — Backend & System Design Interview Guide

This guide is an engineering revision and deep-dive document designed for backend, distributed systems, and system design interviews. It covers the technical decisions, request lifecycles, data contracts, failure modes, and performance trade-offs implemented in GitBot.

---

## 1. 60-Second Project Explanation

> *"GitBot is an AI-powered codebase assistant built with Spring Boot, Java 25, Next.js, and PostgreSQL with pgvector. It allows developers to authenticate with GitHub via OAuth2, discover and synchronize their repositories, and index any codebase into 1536-dimensional vector embeddings stored directly in PostgreSQL.*
>
> *When a developer asks a question, GitBot performs a repository-scoped semantic search using pgvector, pulls neighboring code chunks for context, and streams citations alongside real-time answers back to the browser using Server-Sent Events.*
>
> *On the infrastructure side, it runs across Vercel for the frontend, Render for the containerized backend, and serverless Neon PostgreSQL for both relational entities and vector search, with Redis managing anonymous demo quotas. A key engineering design was keeping the vector store inside PostgreSQL to maintain strict data boundaries and ACID consistency without adding the operational overhead of a standalone vector database."*

---

## 2. 2-Minute Deep Explanation

> *"From an architectural standpoint, GitBot is built on four core pillars: Security, Async Ingestion, Repository-Isolated RAG, and Real-Time Streaming.*
>
> *First, on **Security & Identity**: Authentication uses GitHub OAuth2 requesting `read:user` and `repo` scopes. User access tokens are encrypted with AES-256 before being persisted in PostgreSQL. Session management uses server-side sessions with HTTP-only, `SameSite=Lax`, and `Secure` cookie attributes. During cross-origin deployment between `gitbot.in` and `api.gitbot.in`, we designed a custom SPA CSRF token request handler capable of unmasking Spring Security's XOR-masked tokens while preserving raw-token fallback for local development.*
>
> *Second, on **Repository Sync & Ingestion**: Repositories are synchronized by tracking `latestCommitSha` against `indexedCommitSha`. When indexing is triggered, it runs asynchronously on a dedicated thread pool. It downloads the Git tree via GitHub REST API, filters out binaries and vendor folders, splits source code into 60-line overlapping chunks, generates embeddings in batches of 32 using OpenAI `text-embedding-3-small`, and writes them to PostgreSQL.*
>
> *Third, on **Retrieval-Augmented Generation**: When a user queries a repository, we embed the prompt and execute a cosine similarity search against pgvector, strictly filtering on `repoId` to eliminate cross-tenant data leakage. We automatically fetch adjacent code chunks to preserve function context, fall back to exact SQL keyword matches if semantic search finds sparse results, and bound the assembled context to 12,000 characters before prompt construction.*
>
> *Fourth, on **Streaming & State**: Responses are generated by OpenAI `gpt-4o-mini` and streamed over HTTP/2 using Server-Sent Events via Spring's `SseEmitter` bridged to Project Reactor `Flux`. For unauthenticated visitors, we implemented a zero-persistence demo sandbox backed by atomic Redis rate limiting and IP quotas.*
>
> *The entire system runs containerized on a 512 MiB Render instance, tuned with G1GC and conservative JVM memory limits to operate reliably under strict container cgroup constraints."*

## 5. Request Lifecycle Walkthroughs

### 1. GitHub OAuth2 Login
1. **User Action**: Clicks "Sign in with GitHub" on `gitbot.in`.
2. **Redirect**: Navigates to `GET api.gitbot.in/oauth2/authorization/github`. Spring Security stores authorization request in the session and redirects to GitHub.
3. **Authorization**: User authorizes GitBot on GitHub (`read:user`, `repo` scopes).
4. **Callback**: GitHub redirects to `GET api.gitbot.in/login/oauth2/code/github?code=...&state=...`.
5. **Token Exchange**: Spring Security exchanges authorization code with `github.com` for an access token.
6. **User Sync (`GitHubOAuth2UserService`)**:
   * Fetches user profile from `api.github.com/user`.
   * Encrypts the raw access token using AES-256 (`tokenEncryptor.encrypt(token)`).
   * Upserts the `users` record in Neon PostgreSQL.
   * Creates an `AppUserPrincipal` in the `SecurityContext`.
7. **Session Creation**: Generates a server-side session and sets the `GITBOT_SESSION` cookie (`HttpOnly`, `SameSite=Lax`, `Secure`).
8. **Client Redirect**: `AuthenticationSuccessHandler` redirects the browser to `https://gitbot.in/auth/callback`, which transitions the user to `/dashboard`.

---

### 2. Repository Sync
1. **Trigger**: Dashboard loads or user clicks "Sync All" (`POST /api/repos/sync-all`).
2. **Ownership Check**: Retrieves authenticated `userId` from `CurrentUser`.
3. **Token Decryption**: Decrypts the user's stored GitHub PAT via `userService.decryptAccessToken(user)`.
4. **Remote Fetch**: `gitHubApiClient.listUserRepos(token)` retrieves up to 1,000 repositories via paginated GitHub API calls.
5. **Commit Tracking**: For each repository, `gitHubApiClient.getLatestCommitSha` queries the default branch head commit.
   * `latestCommitSha`: Represents the remote head on GitHub.
   * `indexedCommitSha`: Represents the commit SHA when the codebase was last chunked and embedded.
   * *Distinction*: If `latestCommitSha != indexedCommitSha`, the UI marks the repository as having new commits available without invalidating the existing index prematurely.
6. **Persistence**: Saves discovered repositories to Neon PostgreSQL within a database transaction.

---

### 3. Repository Indexing (Asynchronous Pipeline)
1. **User Action**: Clicks "Index" on a repository (`POST /api/repos/{id}/index`).
2. **Synchronous Validation (`startIndexing`)**:
   * Acquires pessimistic lock on `git_repositories` row (`findByIdAndUserIdForUpdate`).
   * Validates repository is not already `INDEXING`.
   * Sets `indexStatus = INDEXING`, zeroes counters, saves to Neon DB, and returns HTTP `202 Accepted`.
3. **Asynchronous Execution (`indexAsync`)**:
   * Dispatches to `@Async("indexingExecutor")` with a unique `runId`.
   * Fetches Git tree recursively via GitHub Tree API (`getRepoTree`).
   * `CodeFileFilter` excludes binaries, package managers, images, and files $> 100\text{ KB}$.
   * Downloads file blobs sequentially, observing `GitHubRateLimiter` pauses.
   * `CodeChunker` segments files into 60-line overlapping chunks (max 1,500 chars).
   * Chunks are batched into groups of 32 (`VECTOR_BATCH_SIZE = 32`) and sent to OpenAI `text-embedding-3-small`.
   * `vectorStore.add(batch)` inserts embeddings and metadata into `vector_store`.
   * Every 5 files, updates progress counters (`filesProcessed`, `chunkCount`) in Neon.
4. **Completion**:
   * Atomically deletes any older vector chunks for this repository from prior runs (`deleteVectorsExceptRun`).
   * Sets `indexStatus = READY`, records `indexedCommitSha = commitSha`, and updates `indexedAt`.

---

### 4. Authenticated Chat Request
1. **User Prompt**: User submits question in session workspace (`POST /api/chat/sessions/{id}/messages`).
2. **History Lookup**: Retrieves previous 10 messages from `chat_messages` table in Neon.
3. **Semantic Retrieval (`CodeContextRetriever`)**:
   * Embeds question via OpenAI `text-embedding-3-small`.
   * Runs cosine similarity search against `vector_store` with filter: `metadata->>'repoId' = :repoId`.
   * Retrieves top 5 chunks (`top-k: 5`).
   * Fetches adjacent code chunks (`chunkIndex ± 1`) via SQL to preserve surrounding block context.
   * Constrains total context to 12,000 characters.
4. **Prompt Assembly**: Injects code snippets wrapped in `<source path="..." lines="...">` tags into system prompt alongside conversation history.
5. **Streaming Initiation**:
   * Saves user message to `chat_messages` table.
   * Subscribes to OpenAI `gpt-4o-mini` streaming API via Project Reactor `Flux`.
   * Returns `SseEmitter` (`text/event-stream`).
6. **Token Delivery**: Pushes `token` events as OpenAI generates characters, sends `citations` payload, and saves final assistant message to Neon on `done`.

---

### 5. Anonymous Demo Chat
1. **User Prompt**: Unauthenticated visitor chats on `/demo` (`POST /api/demo/chat`).
2. **Rate Limit Verification**: `DemoRateLimiter` increments `demo:rate:{sanitizedIp}` in Redis. If $> 10$ in 60s, throws `429 Too Many Requests`.
3. **Quota Verification**: `DemoSessionRedisService` checks `demo:quota:{sanitizedIp}` in Redis. If used $\ge 5$, throws `429` (Limit reached).
4. **Repository Binding**: Server-authoritative lookup resolves `ManitGitUser/GitBot` repository. Asserts `indexStatus == READY`.
5. **Token Signing**: Increments IP quota in Redis (`TTL: 7200s` / 2 hours) and returns HMAC-SHA256 signed `X-Demo-Token`.
6. **RAG & Stream**: Executes identical semantic retrieval against GitBot's indexed vectors and streams response via SSE **with zero PostgreSQL writes**.

## 6. RAG / Code Search Deep Dive

### Embedding Model & Dimensionality
* **Model**: `text-embedding-3-small`
* **Output Dimensions**: 1,536 dimensions
* **Distance Metric**: Cosine Distance ($1 - \text{cosine similarity}$)
* **Index Type**: Hierarchical Navigable Small World (HNSW)

### Chunking Mechanics
* **Chunk Window**: 60 lines
* **Chunk Overlap**: 10 lines
* **Hard Character Cap**: 1,500 characters
* **Metadata Schema**:
  ```json
  {
    "repoId": "a0d99f3b-612d-4399-b9e7-9bfbd4a0e2aa",
    "repoFullName": "ManitGitUser/GitBot",
    "filePath": "backend/src/main/java/com/example/gitbot/service/ChatService.java",
    "startLine": 120,
    "endLine": 180,
    "chunkIndex": 3,
    "runId": "48f1c8e2-04b3-4f96-b611-667799112233"
  }
  ```

### Cross-Repository Isolation
Cross-tenant and cross-repository data leaks are prevented through multiple independent guarantees:
1. **Database-Level Filter**: Every `SearchRequest` sent to `vectorStore` includes:
   `FilterExpressionBuilder.eq(RagSettings.METADATA_REPO_ID, repoId.toString())`
2. **Ownership Verification**: Before invoking `codeContextRetriever`, `ChatService` requires ownership: `gitRepoService.requireOwned(repositoryId, userId)`.
3. **Neighboring Queries**: Neighbor SQL queries join on `metadata->>'repoId' = :repoId`.

---

### Common RAG Interview Questions

#### Q1: "Why use RAG instead of feeding the whole codebase into a long-context LLM (e.g., Gemini 1.5 Pro / GPT-4o 128k)?"
* **Cost**: Sending 100,000 lines of code on every turn would cost dollars per message. RAG selects the relevant ~500 lines, keeping tokens low.
* **Latency**: Processing massive prompt contexts takes 10–30 seconds before Time To First Token. Bounded RAG context streams in under 2 seconds.
* **Accuracy (Lost in the Middle)**: LLMs suffer attention degradation over massive contexts. Providing high-density, pre-filtered chunks yields superior code reasoning.

#### Q2: "Why pgvector instead of a dedicated vector database like Pinecone, Milvus, or Qdrant?"
* **Operational Simplicity**: PostgreSQL was already required for relational data. Adding pgvector meant zero additional infrastructure to manage, monitor, or pay for.
* **ACID Transactions & Consistency**: Deleting or updating a repository cleans up relational rows and vector chunks in the same transactional boundary, eliminating out-of-sync orphaned vectors.
* **Scale Fit**: For a portfolio/medium-scale codebase assistant ($< 1\text{M}$ vectors), pgvector with HNSW indexes provides sub-100ms retrieval, matching dedicated solutions.

#### Q3: "What happens when a repository is re-indexed?"
* The system does **not** truncate the index immediately. It tags incoming chunks with a new `runId`.
* Existing chats continue retrieving from old chunks while the new index generates.
* Upon full completion, `deleteVectorsExceptRun(repoId, newRunId)` atomically purges the old chunks, preventing downtime or partial-index states.

## 7. Authentication & Security Deep Dive

### Cross-Origin CSRF Lesson (Interview Case Study)

During production deployment with separate subdomains:
* Frontend: `https://gitbot.in` (Vercel)
* Backend: `https://api.gitbot.in` (Render)

#### The Problem:
1. `CookieCsrfTokenRepository` set the `XSRF-TOKEN` cookie on `api.gitbot.in` without a wildcard domain.
2. The browser prevented JavaScript on `gitbot.in` from reading `document.cookie` across origins.
3. The frontend fell back to calling `GET /api/auth/csrf` to retrieve the token via JSON.
4. Spring Security's `XorCsrfTokenRequestAttributeHandler` returned the **XOR-masked token** (`s-KmW9er...`) in the JSON payload.
5. The frontend attached this masked token to the `X-XSRF-TOKEN` request header.
6. The backend's `SpaCsrfTokenRequestHandler` called `super.resolveCsrfTokenValue(...)` whenever a header was present, which assumed the header contained an unmasked raw token.
7. Spring Security compared the raw UUID from the cookie against the XOR-masked header string, failed validation, and rejected mutating requests with **`403 Forbidden`**.

#### The Resolution:
In [`SpaCsrfTokenRequestHandler.java`](file:///home/flux_capacitor/IdeaProjects/GitBot/backend/src/main/java/com/example/gitbot/security/SpaCsrfTokenRequestHandler.java):
```java
if (StringUtils.hasText(headerValue)) {
    String resolved = this.delegate.resolveCsrfTokenValue(request, csrfToken);
    return (resolved != null) ? resolved : super.resolveCsrfTokenValue(request, csrfToken);
}
return this.delegate.resolveCsrfTokenValue(request, csrfToken);
```
* Attempts to resolve via the XOR delegate first: successfully unmasks tokens fetched from `/api/auth/csrf`.
* If unmasking returns `null` (e.g. client read raw cookie via `document.cookie` in local dev), it falls back to `super.resolveCsrfTokenValue(...)`.
* CSRF protection remained strictly enforced without bypassing security.

## 8. Database Design

### Schema Overview

```sql
-- Core entities
users (id UUID PRIMARY KEY, github_id BIGINT UNIQUE, github_username VARCHAR, access_token TEXT, token_scopes VARCHAR);
git_repositories (id UUID PRIMARY KEY, user_id UUID REFERENCES users(id) ON DELETE CASCADE, full_name VARCHAR, index_status VARCHAR, ...);
chat_sessions (id UUID PRIMARY KEY, user_id UUID REFERENCES users(id) ON DELETE CASCADE, repository_id UUID REFERENCES git_repositories(id) ON DELETE CASCADE, parent_session_id UUID REFERENCES chat_sessions(id) ON DELETE SET NULL, ...);
chat_messages (id UUID PRIMARY KEY, session_id UUID REFERENCES chat_sessions(id) ON DELETE CASCADE, role VARCHAR, content TEXT, citations TEXT, ...);
message_reports (id UUID PRIMARY KEY, user_id UUID REFERENCES users(id) ON DELETE CASCADE, session_id UUID REFERENCES chat_sessions(id) ON DELETE CASCADE, message_id UUID REFERENCES chat_messages(id) ON DELETE CASCADE, ...);

-- pgvector table
vector_store (
    id UUID PRIMARY KEY,
    content TEXT,
    metadata JSONB,
    embedding vector(1536)
);
CREATE INDEX spring_ai_vector_index ON vector_store USING hnsw (embedding vector_cosine_ops);
CREATE INDEX idx_vector_store_repo_id ON vector_store ((metadata->>'repoId'));
```

### Relational Integrity & Indexes
* **Cascade Deletes**: Deleting a user purges their repositories, chat sessions, messages, and reports automatically.
* **Set Null on Branching**: Deleting a parent chat session sets `parent_session_id = NULL` on child branches, preserving branched conversation history.
* **Covering Indexes**:
  * `idx_git_repos_user_fullname` on `git_repositories(user_id, full_name)`
  * `idx_chat_sessions_user_created` on `chat_sessions(user_id, created_at DESC)`
  * `idx_chat_messages_session_created_id` on `chat_messages(session_id, created_at, id)`

## 9. Redis Design

| Key Pattern | Data Type | TTL | Purpose |
| :--- | :--- | :--- | :--- |
| `demo:quota:{sanitizedIp}` | String (Integer) | 7,200s (2 hours) | Authoritative message count for an IP in demo mode (max 5). |
| `demo:rate:{sanitizedIp}` | String (Integer) | 60s (1 minute) | Rolling rate limiter tracking API calls per minute (max 10). |
| `demo:session:{sessionId}`| String (Integer) | 7,200s (2 hours) | Tracks active demo conversation turn count, verified via HMAC token. |

### Quota vs. Rate Limit
* **Rate Limit (10 req/min)**: Protects against denial-of-service and burst traffic hitting OpenAI endpoints.
* **Quota (5 messages/2 hours)**: Business boundary offering prospective users an instant test drive while protecting OpenAI API credits from sustained consumption.

## 10. Streaming Architecture (SSE)

### Why Server-Sent Events over WebSockets?
1. **Unidirectional Match**: LLM token generation is strictly server-to-client. The client sends one prompt; the server streams multiple tokens. WebSockets add bidirectional complexity where none is required.
2. **HTTP/2 Efficiency**: SSE runs over standard HTTP. With HTTP/2, multiplexed streams share a single TCP connection without WebSocket upgrade handshakes.
3. **Resilience**: Browsers provide native auto-reconnection for SSE endpoints.

### Markdown Preservation
As tokens arrive character by character, markdown syntax elements (e.g., ```` ```typescript ````, bold `**text**`) are temporarily incomplete. The client utilizes `streamdown` to parse and repair partial tokens on the fly, avoiding layout jitter or raw syntax flashing.

## 12. Scalability Discussion

### What breaks at 10,000 active users?
1. **In-Memory Async Thread Pool**: The `@Async("indexingExecutor")` pool would exhaust JVM heap and thread limits.
   * *Scale Evolution*: Replace in-memory executor with a distributed queue (RabbitMQ / AWS SQS / Redis Streams) and dedicated worker nodes.
2. **GitHub API Rate Limits**: 5,000 requests/hour per user PAT is quickly consumed by frequent full-tree synchronizations.
   * *Scale Evolution*: Implement GitHub App Webhooks (`push`, `repository`) to ingest deltas rather than re-scanning entire trees.
3. **Database Connection Limits**: 100 concurrent workers would saturate Neon's connection pool.
   * *Scale Evolution*: Introduce PgBouncer in transaction mode and deploy read replicas for vector search queries.

## 13. Failure Scenarios

| Failure Event | System Behavior | Recovery Mechanism |
| :--- | :--- | :--- |
| **GitHub API Rate Limited (403)** | `IndexingService` catches `HttpStatusCodeException`, fails fast, and logs error. | Halts indexing immediately; marks repository `FAILED` with descriptive error. |
| **OpenAI Outage / Timeout** | `CodeContextRetriever` or `ChatStreamHandler` throws exception. | Emits structured `error` SSE event to client; avoids saving broken assistant turns. |
| **Server Restarts During Indexing** | In-flight `@Async` job terminates abnormally. | `resetDanglingIndexingJobs` listens to `ApplicationReadyEvent` on startup, finds repositories stuck in `INDEXING`, purges vectors, and resets status to `FAILED`. |
| **Client Disconnects Mid-Stream** | Browser closes tab while LLM is generating. | `SseEmitter` detects broken TCP pipe on next write; `ChatStreamHandler` disposes Project Reactor subscription and saves partial message as `INTERRUPTED`. |

## 16. Important Engineering Trade-offs

| Decision | Why It Was Chosen | Inherent Trade-off | Evolution at Scale |
| :--- | :--- | :--- | :--- |
| **Spring Boot & Java 25** | Robust enterprise ecosystem, type safety, first-class security. | Slower startup and higher baseline memory footprint than Go/Node. | Adopt GraalVM Native Image for sub-second startup if cold starts become an issue. |
| **PostgreSQL + pgvector** | Unified relational and vector storage with ACID transaction boundaries. | Higher index memory usage and slower throughput than specialized vector DBs at $> 10\text{M}$ vectors. | Offload vectors to dedicated vector databases (Qdrant/Milvus) while retaining metadata in Postgres. |
| **Redis for Demo Only** | Zero database persistence for anonymous visitors; sub-ms atomic counters. | Requires a running Redis/Valkey instance alongside Postgres. | Acceptable trade-off to shield primary database from anonymous abuse. |
| **Server-Side Session Cookies** | Protection against token exfiltration; instant server-side revocation. | Requires sticky routing or distributed session store for multi-instance scaling. | Back Spring Session with Redis when scaling to multiple backend replicas. |
| **Server-Sent Events** | Standard HTTP/2 streaming; simpler and more robust than WebSockets. | Unidirectional only; client cannot send messages on the same connection. | Perfectly matches LLM generation patterns; bidirectional needs are nonexistent here. |

## 17. Top 30 Interview Questions & Answers

### Architecture & System Design
1. **How does GitBot work end-to-end?**
   * GitHub OAuth2 authenticates users; repos are synced and commit SHAs tracked. When indexed, files are filtered, chunked, and embedded into pgvector. Questions trigger cosine similarity search against repository-scoped vectors, and context is streamed to the browser via SSE.
2. **Why choose PostgreSQL with pgvector instead of Pinecone?**
   * Eliminates dual-write consistency problems, reduces infrastructure cost, and allows relational queries and vector lookups to be managed in a single ACID database.
3. **How do you prevent cross-repository code leaks in RAG?**
   * All vector similarity searches strictly apply an SQL metadata filter `metadata->>'repoId' = :repoId`.
4. **How do you handle large repositories without running out of memory?**
   * Files are processed sequentially and embeddings are dispatched in batches of 32 chunks, avoiding loading entire codebases into JVM heap.
5. **Why use Server-Sent Events instead of WebSockets?**
   * LLM responses are strictly unidirectional streams. SSE operates over standard HTTP/2 without connection upgrade overhead and features built-in browser reconnection.

### Security & Authentication
6. **Explain the cross-origin CSRF issue you diagnosed during deployment.**
   * The SPA on `gitbot.in` could not read the host-only cookie on `api.gitbot.in`. It fetched the token from `/api/auth/csrf`, which returned an XOR-masked token. The backend handler was resolving the header via the raw resolver, causing a 403 Forbidden. We modified `SpaCsrfTokenRequestHandler` to resolve via the XOR delegate first with raw fallback.
7. **Why use server-side sessions instead of JWTs in localStorage?**
   * Tokens in `localStorage` are vulnerable to XSS exfiltration. HTTP-only, `SameSite=Lax`, `Secure` cookies cannot be accessed by client scripts and can be revoked server-side immediately.
8. **How are GitHub access tokens stored securely?**
   * Tokens are encrypted using AES-256 via Spring Security's `TextEncryptor` before being saved to PostgreSQL and decrypted only when accessing the GitHub API.
9. **What scopes do you request from GitHub and why?**
   * `read:user` (to populate profile details) and `repo` (to read private repositories and retrieve source trees).
10. **What is the purpose of the HMAC token in the demo mode?**
    * The `X-Demo-Token` is a signed payload containing the demo session ID and expiration timestamp, preventing clients from spoofing demo session counts.

### Data & Indexing Pipeline
11. **How does code chunking work in GitBot?**
    * Files are split into 60-line chunks with a 10-line sliding overlap, capped at 1,500 characters, preserving line number metadata for citations.
12. **What files are excluded from indexing?**
    * Binaries, package lockfiles (`package-lock.json`, `pom.xml`), build artifacts (`target/`, `dist/`), and files exceeding 100 KB.
13. **What is the difference between `latestCommitSha` and `indexedCommitSha`?**
    * `latestCommitSha` is the current remote commit head on GitHub; `indexedCommitSha` is the commit head that was embedded into vectors. A mismatch indicates the index is out of date.
14. **How do you handle re-indexing without dropping existing search capability?**
    * Ingestion writes new vectors tagged with a unique `runId`. Old vectors are purged only after the new ingestion completes successfully.
15. **What happens if the backend crashes during an indexing job?**
    * An `ApplicationReadyEvent` listener on startup detects repositories in `INDEXING` state, removes partial vectors, and marks them `FAILED`.

### Performance & Concurrency
16. **Why did the Render deployment initially fail with an Out of Memory error?**
    * The JVM was configured with ZGC and `MaxRAMPercentage=75.0` on a 512 MiB instance. ZGC's native page overhead combined with Metaspace and CodeCache exceeded the cgroup memory limit. Switching to G1GC with 50% max heap, 128m Metaspace, and 48m CodeCache resolved it.
17. **What is the primary cause of latency on the dashboard page?**
    * An N+1 synchronous HTTP loop in `syncAllRepos` fetching commit SHAs sequentially for every repository from the GitHub API.
18. **Why does Neon introduce intermittent query latency spikes?**
    * Neon serverless compute auto-suspends after 5 minutes of inactivity. Resuming compute takes 1.5s–3.5s on the initial query.
19. **What is the Time To First Token bottleneck in chat?**
    * The serial chain: OpenAI embedding generation (~1s) $\rightarrow$ pgvector search (~300ms) $\rightarrow$ OpenAI streaming initiation (~800ms).
20. **How does Redis rate limiting work in demo mode?**
    * Uses atomic `INCR` with a 60-second expiration to cap requests at 10 per minute per IP.

### Database Design & SQL
21. **Why use HNSW over IVFFlat in pgvector?**
    * HNSW provides superior query recall and does not require periodic index retraining as data grows.
22. **What distance operator is used for embeddings?**
    * Cosine distance (`<=>`), because embedding models normalize vectors where angular distance correlates with semantic similarity.
23. **Why use flat UUID fields in JPA entities instead of `@ManyToOne`?**
    * Avoids unintended cascading joins and lazy-loading N+1 query traps. Referential integrity is enforced at the database level.
24. **What happens to child chat sessions when a parent session is deleted?**
    * The foreign key specifies `ON DELETE SET NULL`, preserving the branch's history while unlinking it from the deleted parent.
25. **How are user accounts deleted cleanly?**
    * Deleting a user cascades across `git_repositories`, `chat_sessions`, `chat_messages`, and `message_reports` via foreign-key constraints.

### Scalability & Future Architecture
26. **How would you scale repository ingestion to millions of repositories?**
    * Replace the in-memory `@Async` thread pool with a distributed job queue (e.g., Kafka / SQS) and dedicated container worker pools.
27. **How would you avoid the N+1 commit SHA sync bottleneck?**
    * Register GitHub App webhooks to receive push notifications rather than polling commit SHAs manually.
28. **How would you handle chat sessions across multiple backend instances?**
    * Transition Spring Session to use Redis (`@EnableRedisHttpSession`) so session state is shared across all backend containers.
29. **What would you do if pgvector query times degrade at 50 million chunks?**
    * Partition `vector_store` by `repoId` or migrate vector storage to a dedicated cluster like Qdrant/Milvus while retaining relational metadata in Postgres.
30. **How does GitBot handle client aborts during active SSE generation?**
    * The client sends an `AbortController` signal, closing the HTTP connection. The backend detects the broken pipe, cancels the Project Reactor subscription, and saves the message state as `INTERRUPTED`.
